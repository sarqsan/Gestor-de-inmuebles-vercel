## 1. Alcance real de AG-01 y AG-02

### AG-01 · Alta pública de solicitud

Defecto de la auditoría: el portal construía la solicitud solo con
`candidatoNombre/candidatoEmail/candidatoTelefono`; `firestore.rules` §4 exige además
`nombre`, `email` y `telefono` en `solicitudes.create`. Firestore denegaba el alta, el
handler no esperaba la escritura y la vista mostraba «Solicitud enviada». El candidato
quedaba huérfano y la solicitud se perdía con apariencia de éxito.

Corrección aplicada, sin cambiar el modelo de datos:

- `conIdentidadCanonica()` añade los alias `nombre/email/telefono` conservando `candidato*`.
- `registrarSolicitudPublica()` espera la escritura estricta de `solicitudes` y propaga el
  rechazo. El candidato es un registro secundario: si falla, la solicitud ya persistida no
  se convierte en un error que empujaría a duplicarla; el fallo se registra.
- `guardarSolicitudPublicaFirestore` / `guardarCandidatoPublicoFirestore` no silencian errores
  (a diferencia de los `save*` históricos).
- La vista espera `onCompleteSolicitud`, bloquea el botón mientras envía, muestra el error
  real y solo pinta el acuse de recibo cuando la promesa resuelve.

### AG-02 · Portales por token

Defecto de la auditoría: los enlaces de visita, cuestionario y documentación dependían de
lecturas/escrituras anónimas que las reglas deniegan desde el cierre de 2026-10-14; la ruta
de servidor que los comentarios de las reglas presuponían no existía.

Corrección aplicada:

- Servicio de servidor con la credencial de servicio y el token como capacidad, contra la
  base Firestore con nombre.
- Rutas `GET/POST` por token para las tres superficies.
- Listas blancas cerradas de lectura y escritura; nunca se devuelven notas privadas, scores
  internos, análisis de IA, historial del propietario ni datos de otros candidatos.
- Reserva de visita atómica (slot + invitación + candidato) con precondición de versión;
  cancelación solo libera el slot si sigue vinculado a esa invitación.
- El navegador anónimo ya no se suscribe a `invitaciones`, `slots_visita` ni
  `solicitudes_documentacion`; los contenedores públicos hablan solo con `/api/...`.
- Tokens de capacidad de 128 bits para los enlaces nuevos; se conservan los tokens ya
  emitidos y se restringe el antiguo atajo «id como token» a documentos heredados **sin**
  token (si ya hay token, conocer el id no abre el portal).

## 5. Defectos y bloqueos pendientes

1. **Aceptación manual de los tres enlaces** (visita, cuestionario, documentación) contra un
   entorno con Firestore/Storage y credencial de servicio. No es posible en este sandbox
   (sin Java ni credenciales). Es el único punto que separa este bloque de la aceptación
   completa de AG-02.
2. **Sin rate limiting específico** en las rutas públicas. Hay token de capacidad, listas de
   claves y límite de 256 KB por `Content-Length`, pero el `express.json({ limit: '50mb' })`
   global se aplica antes; conviene un límite/WAF en el despliegue si el tráfico público lo
   requiere. No se ha añadido un limitador en memoria (en serverless daría falsa seguridad).
3. **Adjuntos del alta pública (AG-01)**: `PortalSolicitudPublicaView` registra el estado
   «subido» de los documentos elegidos, pero no sube los binarios; es un comportamiento
   previo a este bloque, fuera de la corrección mínima de AG-01 y no se ha cambiado para no
   ampliar el alcance sin una decisión de producto. La documentación post-visita sí sube por
   la ruta AG-03.2.
4. **Reglas de Storage sin publicar** y sin cambios, conforme a las restricciones del encargo.
   La subida pública de documentación depende de `/api/documentos/publico/*` (AG-03.2), que
   valida el mismo token contra la base con nombre.
5. El servicio de visita devuelve el flag interno `bloqueadoPorPropietario` (sin identidad de
   terceros). Es información de presentación; puede retirarse si se considera interna.
